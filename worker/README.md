# api-bridge — релей к Telegram Bot API

Cloudflare Worker, через который идут **исходящие** запросы к Bot API. Нужен
потому, что прямой канал с сервера теряет около половины запросов: замер `getMe`
серией по 20 дал 14/20 напрямую против 20/20 через воркер.

Входящее направление (вебхук Telegram → `taipan-tkd.ru`) через воркер **не
идёт** и проксировать его не требуется.

Код воркера живёт здесь только для истории и ревью — разворачивается он вручную
через интерфейс Cloudflare. Секрет в репозиторий не попадает: он задаётся
переменной `BRIDGE_SECRET` в настройках воркера.

## Зачем секрет

Без него воркер — открытый релей: кто узнает адрес, тот пользуется квотой и
может слать запросы к Bot API от чужого имени (токен подставляет клиент, но
трафик и лимиты — наши).

## Порядок переключения

На воркере живёт **не только наш бот**, поэтому переключение делается в два
шага, иначе второй бот молча отвалится.

1. **`bridge-transitional.js`** — принимает и с заголовком, и без него.
   Развернуть первым.
2. Перевести клиентов на заголовок (`TELEGRAM_API_SECRET` в `/opt/taipan/.env`
   и `/etc/taipan-monitor.env`), убедиться, что доставка идёт.
3. Перевести второго бота.
4. **`bridge-strict.js`** — требует заголовок у каждого запроса. Развернуть
   последним.

Промежуточное состояние безопасно: переходная версия отвергает **неверный**
заголовок, пропуская только полное его отсутствие.

## Токен в логах Cloudflare

В пути Bot API лежит токен: `/bot<TOKEN>/sendMessage`. Cloudflare по умолчанию
пишет invocation log с полным URL, то есть токен оседает в Observability — та же
проблема, что мы уже чинили в логах сервера (там её создавал `httpx` на уровне
INFO).

Сам воркер печатает только имя метода. Но автоматический invocation log надо
отключить отдельно:

```toml
# wrangler.toml
[observability.logs]
invocation_logs = false
```

или в дашборде: **Worker → Observability → Logs → Invocation logs → off**.

После этого в логах остаются только строки вида `метод sendMessage`.
