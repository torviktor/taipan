# Сертификаты УЦ Минцифры

Здесь лежат два корневых сертификата, без которых бот клуба не может
разговаривать с мессенджером MAX.

## Зачем

API MAX (`https://platform-api2.max.ru`) закрыто сертификатом
`*.max.ru`, выданным **Russian Trusted Sub CA** Минцифры. Этого удостоверяющего
центра нет ни в одном мировом наборе корневых сертификатов, в том числе в
`certifi`, из которого набор берёт `httpx`.

Без этих файлов падают **все** запросы к MAX. Причём падают обманчиво: TLS
доходит до сервера за ~14 мс, по таймингам выглядит как исправная сеть, а
ошибка приходит `CERTIFICATE_VERIFY_FAILED`. Замер 22.08.2026 из контейнера
дал 0 успешных запросов из 20 без bundle и 20 из 20 с ним.

Важно: `update-ca-certificates` эту задачу **не решает** — `httpx` не смотрит
в `/etc/ssl/certs`, он использует набор `certifi`. Поэтому при сборке образа
собирается отдельный bundle (`certifi` + эти два файла), путь к нему уходит в
переменную `MAX_CA_BUNDLE`.

## Сроки действия

| файл | действует до | комментарий |
|---|---|---|
| `russian_trusted_root_ca.pem` | **27.02.2032** | корень, самоподписанный |
| `russian_trusted_sub_ca.pem` | **06.03.2027** | ← этот истечёт первым |

`Sub CA` подписан корнем, цепочка проверяется `openssl verify` и сходится.

**Sub CA никем не продлевается автоматически.** В отличие от нашего
Let's Encrypt, за которым следит certbot, эти файлы обновляются только руками —
и если этого не сделать, в марте 2027 бот в MAX замолчит без единого сообщения
об ошибке в привычных местах.

За сроком следят два независимых механизма, чтобы это не стало сюрпризом:

* сборка образа печатает срок каждого сертификата в лог и ругается, если
  осталось меньше 60 дней;
* ежедневная сводка `taipan-monitor` показывает остаток дней и поднимает
  тревогу за 30 дней.

## Как обновить

1. Скачать свежие файлы:

   ```sh
   curl -o russian_trusted_root_ca.pem https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer
   curl -o russian_trusted_sub_ca.pem  https://gu-st.ru/content/Other/doc/russian_trusted_sub_ca.cer
   ```

2. Убедиться, что внутри PEM (`head -1` → `-----BEGIN CERTIFICATE-----`).
   Если внутри DER, сконвертировать:
   `openssl x509 -inform DER -in файл -out файл.pem`

3. Проверить, что цепочка сходится:

   ```sh
   openssl verify -CAfile russian_trusted_root_ca.pem russian_trusted_sub_ca.pem
   ```

4. Пересчитать суммы и **обновить их в `backend/build_ca_bundle.py`** — иначе
   сборка остановится с явным сообщением о расхождении:

   ```sh
   sha256sum *.pem
   ```

5. Обновить даты в таблице выше и в `build_ca_bundle.py`.

6. Выкатить и убедиться, что запросы к MAX проходят:

   ```sh
   docker compose exec -T backend python -c "from app.services.max_bot import get_me; print(get_me())"
   ```

## Почему файлы лежат в репозитории, а не скачиваются при сборке

Скачивание при сборке пробовали — отказались. Оно ставит деплой в зависимость
от доступности постороннего сайта: лежит `gu-st.ru` — не выкатывается ничего,
включая правки, никак с MAX не связанные. Вдобавок в момент плановой ротации
`Sub CA` закреплённая контрольная сумма перестала бы совпадать, и сборка
падала бы в самый неподходящий момент.

Проверка «не пора ли обновить» вынесена из критического пути: этим занимается
`scripts/check_ca_certs.py`, который ходит в сеть и сравнивает наши файлы с
тем, что отдаёт `gu-st.ru`. Его запускает еженедельная задача монитора; на
сборку он не влияет.
